# Technical Specification

This is the technical specification for the spec detailed in @.agent-os/specs/2025-01-26-structure-cleanup/spec.md

> Created: 2025-01-26
> Version: 1.0.0

## Technical Requirements

### File Structure Cleanup
- Remove empty `src/app/` directory completely
- Remove broken duplicate components in `src/modules/*/components/` with outdated import paths
- Remove broken duplicate hooks in `src/modules/*/hooks/` with outdated import paths
- Preserve only business logic services, constants, and types in `src/modules/`

### Library Consolidation
- Move all contents from `src/lib/` to `lib/` directory
- Maintain `lib/generated/prisma/` structure (generated by Prisma)
- Update all import paths from `@/src/lib/*` to `@/lib/*`
- Ensure no functionality is lost during consolidation

### Tab-Based Component Organization
- Restructure `app/simulation/components/` into feature-based tabs:
  - `tabs/parameters/` - All parameter-related components
  - `tabs/price-projection/` - All price projection components  
  - `tabs/strategy/` - All strategy components (future)
  - `tabs/results/` - All results components
  - `shared/` - Components used across multiple tabs
- Create `index.ts` barrel exports for each tab
- Maintain existing component functionality and props

### Import Path Updates
- Update `tsconfig.json` paths configuration for consolidated structure
- Fix all relative imports to use absolute imports with path mappings
- Ensure all components can find their dependencies
- Update any hardcoded paths in configuration files

## Approach Options

**Option A:** Big Bang Restructure
- Pros: Complete cleanup in one go, clear before/after state
- Cons: High risk of breaking imports, difficult to test incrementally

**Option B:** Incremental Migration (Selected)
- Pros: Lower risk, can test each step, easier to debug issues
- Cons: Takes longer, temporary inconsistent state

**Rationale:** Incremental approach reduces risk of breaking the application and allows for testing at each step. Given the complexity of import dependencies, this is the safer approach.

## External Dependencies

No new external dependencies required. This is purely a structural reorganization using existing tools and frameworks.

## Implementation Steps

1. **Phase 1: Remove Broken Duplicates** (Low Risk)
   - Delete empty `src/app/` directory
   - Remove broken components in `src/modules/*/components/`
   - Remove broken hooks in `src/modules/*/hooks/`

2. **Phase 2: Consolidate Libraries** (Medium Risk)
   - Move `src/lib/` contents to `lib/`
   - Update import paths in affected files
   - Test functionality after each service move

3. **Phase 3: Reorganize Components** (High Risk)
   - Create new tab-based structure
   - Move components to appropriate tabs
   - Update internal imports and exports

4. **Phase 4: Update Configuration** (Low Risk)
   - Update `tsconfig.json` path mappings
   - Fix any remaining import issues
   - Final testing and validation

## Risk Mitigation

- Test application functionality after each phase
- Keep git commits small and focused for easy rollback
- Maintain backup of working state before major changes
- Use TypeScript compiler to catch import errors early
